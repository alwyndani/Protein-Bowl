# CLAUDE.md — Protein Bowl

Engineering instructions for Claude Code. The code is the source of truth; `PROGRESS.md` is the single status/test tracker; `docs/OPERATIONS.md` covers production configuration, jobs, backup and rollback; `server/TESTING.md` covers test-database isolation. The detailed per-phase history (P5–P11C, role simplification) that used to live here is in git history of this file.

## 1. Product and scope
Protein Bowl: customer web app (Vite + React 19), customer mobile app (Expo/React Native), one Express REST API, one PostgreSQL database. Web and mobile share the same backend. **Exactly six roles**: `CUSTOMER`, `CHEF`, `NUTRITIONIST`, `TRAINER`, `PROCUREMENT`, `SUPER_ADMIN`. Retired (still listed in the Prisma enum; they never authorize anything; shrinking the enum would be a separate migration that needs its own approval): `MESS_CUSTOMER`, `MD`, `DELIVERY`, `POS`, `BAKERY_FMCG`, `TEPACHE_ERP`, `SWIGGY_ZOMATO`. Removed domains: POS, Bakery/FMCG ERP, Tepache ERP, driver workspace, MD, aggregators, HRM, finance, CMS, SRS generator. Packaged-food and Tepache **products** stay in the customer catalogue. Never rebuild, replace architecture, or delete working modules without approval.

**PERMANENT PAYMENT POLICY — ONLINE payment only.** No Cash on Delivery, cash collection, pay-at-door, wallet payment or driver settlement anywhere. `POST /orders` accepts only `ONLINE` (omitted = ONLINE); `COD` → 422 `COD_NOT_ALLOWED`; `COMMERCE_COD_ENABLED=true` fails startup. Legacy rows may carry the string `COD`; they are readable, non-payable, and never enable new COD.

## 3. Backend rules
- Base `/api/v1`. Layering `routes → controller → service`; Zod validation (`validateBody/Query/Params`, strict bodies for money/state-changing calls); `AppError(message, status, code)` with stable codes; envelope `{success, message?, data?, error?}` (`ApiResponse`). ESM, imports end in `.js`. One shared Prisma singleton (`config/database.ts`).
- **Authentication is database-authoritative** (`authenticateToken`): every request loads the user; non-ACTIVE/soft-deleted → 401; roles come from current `UserRoleAssignment` rows filtered through `authz/approvedRoles.ts`; JWT role claims are never used. An account with no approved role → 403 `NO_APPROVED_ROLE`. Access JWT 15 min; refresh token 7 d hashed in DB, HttpOnly cookie (web) or JSON body on `/auth/mobile/*` (mobile; customer-only, header contract, browser exclusion).
- **Authorization**: static permission catalogue `authz/permissions.ts` (no implicit SUPER_ADMIN bypass); `requireExactRoles`, `requireCustomerRole` (literal CUSTOMER) for customer endpoints; branch scope via `authz/branchScope.ts` (`authorizeBranch`, `assertResourceBranchAccess`): never trust a client branch id; a foreign branch → 403, an omitted branch means "my branches".
- **Identities** are separate: a staff account is never a customer. Public registration creates CUSTOMER only. Staff are created by SUPER_ADMIN invitation (`StaffInvitation`, hash-only single-use token; delivery `manual` or `email`), activated through `/auth/staff/accept-invite`; staff password policy 12–128 chars (`utils/staffPassword.ts`); sensitive admin actions need a password step-up proof (`X-Step-Up-Token`, `requireStepUp`).
- **Password reset** for any ACTIVE approved-role account: `POST /auth/forgot-password` (always generic 202; per-IP limiter + per-account cooldown; mail sent off the response path), `POST /auth/reset-password` (hash-only single-use expiring `PasswordResetToken`, newest link only, all sessions revoked, staff keep the staff policy). Mailer `modules/email` (`EMAIL_PROVIDER` none | log (dev only) | resend; production must set it explicitly).
- **Money**: Decimal only; `pricing.service.ts` with `CommercePolicy` from `COMMERCE_*` env is the single pricing authority; clients display server values.
- **Orders**: `OrderTransitionService` is the ONLY writer of `Order.status` after creation (allow-list, actor check, payment gate, compare-and-set, `OrderEvent` + audit). `PaymentSettlementService` is the only path that marks an order paid (verified provider evidence only; webhook raw-body signature verified first; duplicates/late/mismatched captures kept and flagged, never auto-refunded). Cancellation and refunds go through `CancellationService` / `RefundService` (full refunds only; refund intent created in the same transaction as the cancellation; the provider is contacted after commit; reconciliation guarantees completion).
- **Cancellation policy**: customer may cancel PENDING and CONFIRMED. Paid orders ACCEPTED/PREPARING/READY: the customer can only *request* cancellation (`CancellationRequest`); SUPER_ADMIN approves (order cancelled + FULL refund atomically) or declines with a reason. Unpaid online food orders are expired by `OrderExpiryService` after `UNPAID_ORDER_EXPIRY_MINUTES` (default 15; 0 disables) only when no sign of payment exists.
- **Kitchen**: SUPER_ADMIN routes a paid order to a branch; CHEF (own branches) accepts → prepares → ready. **Delivery**: SUPER_ADMIN operates delivery (dispatch, verify the customer's 6-digit Delivery Code, report failure, retry/resume, take over, undeliverable → cancel + full refund, exceptional override); there is no driver role. DELIVERED is reachable only through a verified `DeliveryProof`.
- **Kerala Mess** is a customer feature on the CUSTOMER identity (approved account, plans, paid subscription, meals, pause, chef batches, SUPER_ADMIN-operated bulk delivery and handover). Same ONLINE-only rule.
- **Nutrition**: customer request → NUTRITIONIST claims (race-safe) → reads the assigned client's health profile (audited) → publishes plan versions. Health data is visible only to the claiming nutritionist; SUPER_ADMIN has no break-glass.
- **Coaching**: SUPER_ADMIN assigns trainer ↔ customer (`TrainerAssignment`); TRAINER manages `WorkoutPlan`s only for assigned clients (no health data); the customer logs progress (`WorkoutLog`).
- **Procurement**: suppliers, purchase orders DRAFT → ORDERED → PARTIALLY_RECEIVED/RECEIVED or CANCELLED, goods receipt writes receipt + stock movements + stock in one transaction, stock never negative, branch-scoped.
- Never log or audit secrets, tokens, passwords, delivery codes, reset links or provider payloads.

## 4. Frontend rules
Services in `src/services/*Service.ts` over `ApiClient` (use `requestData` for flows that must not treat failure as success; **never swallow an API failure and continue as if it worked**). Display server-derived state (`payment`, `cancellation`, `cancellationRequest`, `refund`, `delivery`) and never turn a server `false` into `true`. Role workspaces are presented only to a session holding the matching backend role (`utils/roleGuard.ts`, UX only). Clinical values are shown as recorded: a missing value is "Not provided", never a default. No new mock runtime data; the DEV-only role sandbox may stay development-only. Mobile: customer only, tokens in SecureStore/memory only, all endpoint strings confined to their API modules (static guards enforce this), no logging.

## 5. Database and migrations
`server/prisma/schema.prisma`; migrations are forward-only and applied with `prisma migrate deploy` only. NEVER: `db push`; `migrate reset` on any non-disposable database; editing applied migrations; touching `_prisma_migrations`. New migration folders must sort after the current tail and be replayed on a disposable database before any real one. Three prepared migrations are included in the staged changes; nothing has been committed to Git yet. They are, in this order: `20261020100000_role_simplification_admin_actors` (additive columns and CHECK constraints for SUPER_ADMIN-operated delivery), `20261031120000_trainer_procurement_foundation` (trainer assignments, workout logs, suppliers, purchase orders/receipts, password reset tokens, cancellation requests) and `20261101120000_health_exercise_unanswered` (`health_biometrics.hasExercise` becomes nullable so an unanswered question is no longer stored as "No"; no existing value is rewritten). **None has been applied to any development or production database**; the first two already exist on the disposable test database `pb_ci_test`, the third on no database. Hand-run helper SQL for the first migration (`precheck_migration_a.sql`, `postcheck_migration_a.sql`, `20261020100000_role_simplification_admin_actors/rollback.sql`) is under `server/prisma/proposed/role-simplification/`. Before any real database: take a verified backup, replay the whole chain on a disposable PostgreSQL (`server/TESTING.md`, `src/tests/preparedMigrations.migration.test.ts`) and compare the result with `schema.prisma` using `prisma migrate diff`; none of that has been run yet. No enum-shrink or table-dropping migration exists in the repository; such a migration would be destructive and needs its own approval.

## 6. Testing
- Web: `node automation/run-web-tests.mjs` (Vitest + jsdom), `npm run typecheck:web`, `npm run build`.
- Mobile: `cd apps/mobile && npx tsc --noEmit && npm test`.
- Server typecheck: `npm run typecheck:server` (needs `prisma generate`; covers `server/src` only — tests, scripts and seeds are not type-checked).
- Server tests are integration tests against real PostgreSQL and run ONLY against an isolated database named by `TEST_DATABASE_URL` (validated in `src/tests/testDatabase.ts`; never the development or shared database). Database-free subset: `testDatabase.unit`, `purchasing.unit`, `invite-config`, `email.unit`. Procedure: `server/TESTING.md`, `server/scripts/verify-isolated.sh`.
- Every change to auth, RBAC, ownership, pricing, orders, payments or health data needs regression tests; never weaken a test to make it pass. Do not claim a feature complete from code or mocked tests alone.

## 7. Safety rules for Claude sessions
- No commit/push, no migration applied, no connection to shared/development/production databases, no account changes, no production deploy, no live payments or live credentials without explicit approval.
- `.claude/hooks/pb-guard.mjs` and `.claude/settings.json` are user-owned guards (shell allow-list; blocks database/Prisma commands except offline `validate`, file deletion, `.env` access). Do not circumvent them through other tools; when blocked, give the user one exact command.
- `server/scripts/reconcilePayments.ts` carries a `TEMPORARY-H1-DO-NOT-MERGE` target guard; production uses `scripts/reconcilePaymentsProd.ts` (dry run by default, `--apply` to act) once verified. Do not remove the old guard before that verification.
- Stop and ask for product decisions (pricing, tax, fees, refund policy, timeouts) and for anything destructive or outward-facing.
