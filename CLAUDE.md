## 1. Purpose
Protein Bowl is a food-tech platform: customer web app, React Native mobile app, one Express REST API, one PostgreSQL database, and internal ERP/operations modules, gated by RBAC. Web and mobile MUST share the same backend and database. This is an existing project migrated from Antigravity IDE — never rebuild, replace architecture, or delete modules that look incomplete.

## 4. Backend architecture
- Base path `/api/v1`. Mounted: auth, customers, products, recipes, cart, checkout, orders, mess, diets, kds, procurement, delivery, pos, fmcg, tepache, md, hrm, finance, cms, plus `/admin/*` (SUPER_ADMIN platform administration; MD read-only on branches), `/staff/me|permissions` (staff self-service), `/auth/staff/accept-invite`, plus `GET /health`.
- Layering: `*.routes.ts` (middleware chain) → `*.controller.ts` → `*.service.ts`. Zod validators exist for auth, customer, diet, recipe, cart, order only.
- Response envelope: `{success, message?, data?, error?}`; `ApiResponse` helper in `utils/apiResponse.ts`, though cart/order controllers call `res.json` directly. Errors: throw `AppError(message, status, code)`; `errorHandler` maps `AppError` and `ZodError` (422).
- Monetary logic: `modules/commerce/pricing.service.ts` is the single Decimal-safe pricing authority (cart, checkout preview AND order creation) and takes a **`CommercePolicy`** (`config/commercePolicy.ts`, P7A) - there is NO default policy and no hard-coded fee/threshold/tax rate. Tax is EXCLUSIVE, per line, rounded HALF_UP, order tax = sum of rounded line taxes; delivery/packaging fees and deposits are untaxed.
- Order creation (P7A) is ONE transaction under a per-customer Postgres row lock (`modules/commerce/checkoutLock.ts`, shared with cart mutations): customer-scoped idempotency (`@@unique([customerProfileId, idempotencyKey])`, key REQUIRED via header `x-idempotency-key`, 8-128 chars), `requestFingerprint` (same key + different request -> 409 `IDEMPOTENCY_KEY_REUSED`), pricing with the current policy + immutable `pricingSnapshot`, minimum-order enforcement, OrderItem/address snapshots, `OrderEvent` (null -> PENDING), `ORDER_CREATED` audit, and deletion of exactly the ordered cart lines. Order numbers are `PB-YYMMDD-XXXXXX` (CSPRNG; a collision retries the transaction, 5 attempts then 503 `ORDER_NUMBER_UNAVAILABLE`). Responses are the customer DTO (`order.dto.ts`), never the raw row.
- Prisma: all application services/controllers use the shared singleton (`import { prisma } from '../../config/database.js'`; logs `error`/`warn` only, `error` in production). Never add `new PrismaClient()` to app code. Intentional standalone clients remain only in `prisma/seed*.ts` scripts and test fixtures (`src/tests/*`).

## 6. Authentication
- **The database is the source of truth for every authenticated request (P6A):** `authenticateToken` verifies the JWT signature/expiry, then loads the user; unknown, soft-deleted or non-ACTIVE (PENDING/SUSPENDED/DEACTIVATED) accounts get `401 ACCOUNT_INACTIVE` immediately, and `req.user.roles` is rebuilt from the CURRENT `UserRoleAssignment` rows (JWT role claims are never used for authorization). Refresh (`rotateRefreshToken`) and login also reject inactive/soft-deleted users; refresh denial revokes all of the user's sessions (`AuthService.revokeAllRefreshTokens`) and is audited. Cost: one indexed PK query per request.
- Access JWT (15m default) via `Authorization: Bearer`; refresh token (7d) stored hashed-in-DB (`RefreshToken`), sent as HttpOnly cookie `pb_refresh_token` (body `refreshToken` also accepted — used by mobile), rotated on refresh.
- Web keeps access token in memory only (`ApiClient`). Mobile uses expo-secure-store.
- Rate limits (per IP, env-configurable `RL_*`): login 20/15min, register 10/hour, refresh 60/15min, general `/api/v1` 600/15min (health exempt). Limits are effectively off under `NODE_ENV=test` unless a test sets `RL_*_MAX` before importing the app (see `ratelimit*.test.ts`). `RL_DISABLED=true` works only outside production. Set `TRUST_PROXY` when behind a reverse proxy.
- Public registration allows only `CUSTOMER` or `MESS_CUSTOMER` (customer password policy: min 8, unchanged). Staff accounts are created ONLY through the staff lifecycle below (or the CLI bootstrap for the first SUPER_ADMIN) - never by public registration.
- **Staff lifecycle (P6B):** SUPER_ADMIN `POST /admin/staff` (needs step-up) → account `PENDING` with an unusable random placeholder password hash, staff roles + branches, and an invitation → one-time setup link returned ONCE (`deliveryMode: "manual"`, `sentByEmail: false`; nothing is emailed) → staff `POST /auth/staff/accept-invite {token, password}` (public, rate-limited `RL_ACCEPT_INVITE_*`) → in one transaction: invitation consumed, password set, status `ACTIVE`, earlier sessions revoked, `STAFF_INVITATION_ACCEPTED` audited → staff logs in normally. Invitation tokens: 32 random bytes (hex), only the SHA-256 hash is stored (`StaffInvitation.tokenHash`), single use, expire after `INVITE_TTL_HOURS` (default 72h), revocable/reissuable (`POST /admin/staff/:id/invitation`, PENDING accounts only - never a password reset for ACTIVE users). Every invalid/expired/used/revoked/ineligible token returns the same `400 INVALID_INVITATION`. The token travels in the setup link's URL fragment. `INVITE_DELIVERY=manual` is the only supported mode until the email adapter (P14) implements `InvitationDelivery`: it is OPTIONAL (defaults to manual) in development/test but REQUIRED in production - a missing or unsupported value fails config validation at startup (no silent fallback). Manual mode always reports `deliveryMode: "manual"`, `sentByEmail: false` and never claims an email was sent. Any test that simulates a production boot must set `INVITE_DELIVERY=manual` (plus `CORS_ALLOWED_ORIGINS`).
- **Staff password policy (decision D7):** 12-128 chars, ≥3 of 4 character classes unless a 20+ char passphrase, not a known/default password, must not contain the email name or the person's name (`utils/staffPassword.ts`). Staff 2FA is deferred.
- **Password step-up:** `POST /admin/step-up {password}` (SUPER_ADMIN, rate-limited `RL_STEPUP_*`) returns a short-lived proof (`STEP_UP_TTL_SECONDS`, default 300s) sent as `X-Step-Up-Token`. It is a signed JWT with a distinct audience, bound to the user and an HMAC fingerprint of their CURRENT password hash (changing the password invalidates it); `verifyAccessToken` rejects it as an access token. Required for: create staff, reissue invitation, assign/revoke role, assign/revoke BRANCH, deactivate, activate. Not required for staff profile updates or read endpoints. It is time-limited, not single-use (single-use would need server-side storage); step-up tokens never appear in the audit log.

## 7. RBAC roles (`RoleEnum`, verified)
CUSTOMER, MESS_CUSTOMER, SUPER_ADMIN, MD, NUTRITIONIST, TRAINER, CHEF, PROCUREMENT, DELIVERY, POS, BAKERY_FMCG, TEPACHE_ERP, SWIGGY_ZOMATO. Do not change role semantics.
Middleware (`auth.middleware.ts`): `authenticateToken` (DB-authoritative); `requirePermission('kds:read'|…)` (static catalogue in `authz/permissions.ts`; **no implicit SUPER_ADMIN bypass** — SUPER_ADMIN holds permissions explicitly; MD holds READ permissions only); `requireRole([...])` (**staff/admin APIs only — SUPER_ADMIN always passes**); `requireCustomerRole` (literal CUSTOMER; no SUPER_ADMIN bypass); `requireExactRoles([...])` (listed roles only; no bypass). `rbac.middleware.ts` also has `requireRoles` (SUPER_ADMIN bypass; used only in `auth.routes`). RULE: customer-context endpoints must use `requireCustomerRole`/`requireExactRoles`, never `requireRole`.
**Role scope catalogue (`authz/roleScopes.ts`):** SUPER_ADMIN=GLOBAL; MD=GLOBAL_READ (read-only visibility; no operational mutations, staff/role/security administration, or clinical health data); NUTRITIONIST/TRAINER=ASSIGNMENT; CHEF/PROCUREMENT/POS/BAKERY_FMCG/TEPACHE_ERP/SWIGGY_ZOMATO=BRANCH (facility roles get NO global access); DELIVERY=BRANCH_SELF (own work only); CUSTOMER/MESS_CUSTOMER are customer identities. Staff and customer identities stay separate (no account may hold both; `hasMixedIdentity`/`findMixedIdentityUserIds` detect conflicts and only report); CUSTOMER/MESS_CUSTOMER/SUPER_ADMIN are in `NON_ASSIGNABLE_ROLES` for future staff-administration APIs (SUPER_ADMIN is created only by the P6B bootstrap CLI).
**Branch scope (`authz/branchScope.ts`):** `resolveBranchScope` (DB) → `resolveBranchFilter(scope, mode, requestedBranchId)`: branch-scoped callers get their assigned branches; an omitted branch means "my branches" (NEVER all); a foreign branch → 403 `BRANCH_FORBIDDEN`; no assignment → 403 `NO_BRANCH_ASSIGNMENT`; only SUPER_ADMIN (and MD for reads) can get `all`. Applied to KDS, procurement, POS and delivery endpoints (denials are audited). Delivery drivers only see/update their own assignments (client `driverId` spoofing → 403). Use `authorizeBranch` / `assertResourceBranchAccess` in new operational endpoints; never trust a client branchId.
**Administration permissions (P6B, `authz/permissions.ts`):** `staff:admin`, `audit:read`, `branch:write` = SUPER_ADMIN only; `branch:read` = SUPER_ADMIN + MD. MD is NOT a staff/security administrator and cannot read the audit log.
**Role guardrails (`StaffAdminService`):** SUPER_ADMIN/CUSTOMER/MESS_CUSTOMER are never assignable or revocable through the API (`NON_ASSIGNABLE_ROLES`); nobody can change their own roles, branches or deactivate themselves; an account must keep ≥1 role (`LAST_ROLE`); staff targets only (customers are indistinguishable from not found); mixed customer/staff identities are refused (`MIXED_IDENTITY`); duplicate assign / revoking an unheld role are deterministic no-ops (`changed:false`, not audited); role changes take effect on the next request (P6A).
**Branch rules:** assignable branches must exist and be active; `EmployeeBranchAssignment` is authoritative; the first assigned branch becomes the primary (`assignedBranchId`); revoking the primary re-points it to the earliest remaining assignment or clears it (it can never dangle, because scope = assignments ∪ primary). A branch with ACTIVE/PENDING staff cannot be deactivated (`BRANCH_HAS_ACTIVE_STAFF`). Branch `code` is immutable; branches are never deleted.
**Deactivation:** requires a reason; revokes ALL refresh sessions and active invitations; the old access token dies on the next request (P6A); `LAST_SUPER_ADMIN` guard runs in a SERIALIZABLE transaction (concurrent mutual deactivation cannot leave zero administrators). Activation requires a reason, refuses PENDING (use the invitation), soft-deleted, and never-completed-setup accounts (`PASSWORD_SETUP_INCOMPLETE`).
`MESS_CUSTOMER` is LEGACY / DEPRECATED FOR FUTURE RECONCILIATION. Target (decided): CUSTOMER is the canonical customer identity for Customer Portal AND Kerala Mess; Mess entitlement = the customer's MessAccount. Until a controlled future migration, customer Mess endpoints accept CUSTOMER and legacy MESS_CUSTOMER; MESS_CUSTOMER is not accepted on diet/commerce/profile APIs. Do not delete or rewrite the role without an approved phase.

## 8. Customer vs staff boundaries
One customer account, two customer experiences (Customer Portal, Kerala Mess). Customers never get staff/ERP permissions. Public register cannot mint staff roles. Customer-private routes derive identity from `req.user.userId` (JWT) → `CustomerProfile` lookup; never accept `customerId` from the client. ## 9. Security rules and known gaps
Rules: backend authorization + ownership checks are authoritative; frontend hiding is not security; never leak costing/clinical notes/SOP/supplier/ERP metadata in public DTOs; least-privilege for health data (diet health-profile access is limited to NUTRITIONIST/SUPER_ADMIN with claim checks in `diet.service`).
Phase 4C (2026-10-07) fixed: cart/diet/mess customer-role guards (SUPER_ADMIN and staff are blocked from customer-context APIs); CORS allow-list + Origin check on state-changing requests (`CORS_ALLOWED_ORIGINS`, falls back to `CLIENT_URL` outside production; production startup fails without it; no-Origin requests such as mobile/curl are allowed; a disallowed origin gets no CORS headers, mutating requests get 403 `ORIGIN_NOT_ALLOWED`); auth + general rate limits; `JSON_BODY_LIMIT` (default 256kb; oversized -> 413, malformed JSON -> 400); invalid HTTP `4404` in mess controller; Payment default; seed production guard (`prisma/seedGuard.ts`: NODE_ENV=production seeds only recipes/products, never demo users); web/mobile demo credentials gated behind `import.meta.env.DEV` / `__DEV__`; shared Prisma singleton.
Body limit rationale: legitimate max today is a 7-day nutritionist plan (~20-45KB); a verbose 30-day, 6-meals/day plan is ~90KB; the validators allow up to 365 days (~1MB) but no UI sends that. Binary/lab-report uploads need a dedicated upload route later, not bigger JSON limits.
P6A (2026-10-08) fixed: S16 (deactivated users / stale roles — see §6), S17 (cross-branch reads/writes), SUPER_ADMIN and MD access to customer health data (see §18), `/auth/rbac-test` is registered ONLY when `NODE_ENV !== 'production'`, and the web role-demo switcher (BrandHeader) is DEV-only; additionally the production web build only presents a staff dashboard to a session that holds the matching backend role (`utils/roleGuard.ts`, presentation hygiene only — the backend authorizes every call). Operational DTOs were minimized (KDS: customer full name only; delivery: order basics + address snapshot).
P6B (2026-10-08) delivered: staff/branch/audit administration APIs, invitation onboarding, step-up, 12-char staff password policy, CLI bootstrap, `/staff/me`, audit-read API (SUPER_ADMIN-only, payload re-sanitized on output). Audit events: STAFF_CREATED, STAFF_INVITED, STAFF_INVITATION_REISSUED, STAFF_INVITATION_ACCEPTED, STAFF_INVITATION_REJECTED, STAFF_UPDATED, STAFF_ACTIVATED, STAFF_DEACTIVATED, ROLE_ASSIGNED, ROLE_REVOKED, BRANCH_ASSIGNED, BRANCH_REVOKED, BRANCH_CREATED, BRANCH_UPDATED, BRANCH_DEACTIVATED, SUPER_ADMIN_BOOTSTRAPPED, STEP_UP_FAILED, STEP_UP_DENIED, ADMIN_ACTION_DENIED (+ P6A events). Admin audit rows are written in the SAME transaction as the change; denials are best-effort.
P6C (2026-10-08) delivered the production Super Admin web workspace (`src/components/admin/*`, `services/adminService.ts`): staff list (server-side search/status/role/branch filters + pagination), staff detail/profile edit (no step-up), invite staff with a MANUAL one-time invitation hand-off ("NO EMAIL WAS SENT"; link held in transient component state only, dismissed = gone, reissue to get a new one), role assign/revoke, branch assign/revoke, activate/deactivate (reason + explicit confirmation), invitation reissue, branch administration, read-only audit log, informational permissions view, and the public `/staff/accept-invite` page (token read from the URL fragment `#token=`, held in module memory, fragment scrubbed with `history.replaceState`; rendered by `main.tsx` WITHOUT the app shell). ## 17. Money / pricing safety
- Backend is authoritative; never trust client prices/totals. Use `Decimal` (Prisma runtime Decimal), never float arithmetic, for money.
- Commercial values are policy, not code (P7A): `CommercePolicy` comes from validated `COMMERCE_*` environment variables (`server/.env.example`). In PRODUCTION every value must be set explicitly or startup fails; outside production a missing value falls back to clearly labelled DEVELOPMENT example values (`policySource: DEVELOPMENT_DEFAULTS` in the snapshot) that are NOT Protein Bowl policy. Only `COMMERCE_TAX_MODE=EXCLUSIVE` and untaxed delivery/packaging are supported (anything else fails startup). Tests inject a deterministic policy (`tests/setup.ts` sets explicit TEST-FIXTURE values: 40.00 / 499.00 so legacy expectations stay stable). The real fee, threshold, packaging, minimum order, quantity caps, tax rates and COD decisions remain **PRODUCT DECISION REQUIRED** (P7-D1..D8). `Product.taxRate` and `OrderItem.taxRate` have NO default any more (migration `p7a_remove_tax_rate_defaults`; both stay NOT NULL): every Product creation must state its tax rate and every OrderItem snapshot is written from the calculated rate. Existing stored rates (including legacy 0.05 rows) are preserved untouched. Seeds and test fixtures supply explicit rates (explicit demo/test data, not policy).
- Payments: no gateway. Orders must never become PAID automatically. Keep order `status` and `paymentStatus` separate. `Payment.status` now defaults to `PENDING`; a payment must never be marked SUCCESS/PAID without verified gateway confirmation. Payment status enum design is deferred. Do not integrate Razorpay/Stripe/UPI until instructed.

## 18. Health-data access
Health biometrics/clinical notes are private to the owning customer. Staff access is ONLY the nutritionist assigned (claimed) to that request: all nutritionist clinical routes (`/diets/nutritionist/*`, claim, health-profile, plan creation) require the literal NUTRITIONIST role (`requireExactRoles`), and the service re-checks assignment. SUPER_ADMIN and MD have NO access (no bypass, cannot claim requests, no break-glass implemented — any future exceptional access needs its own reason + authorization + audit design). Health-profile access and denials are written to `AuditLog` (payload carries ids only, never health data). Staff DTOs must not leak to public/customer projections and vice versa. Calculations stay server-side.

## 19. Recipe / Product boundary
Recipe = culinary/nutrition/prep definition. Product = purchasable offering (`Product.recipeId` optional). ProductVariant = SKU. Not every Recipe is a Product and not every Product has a Recipe. No cart/order/payment/inventory logic in Recipe. Recipe source files in `src/data/recipes/` + `recipeDatabase.ts` are import/seed sources (and still used at runtime by several web components — see §20).

## 21. Coding conventions
- Backend ESM TS, strict mode; relative imports end in `.js`. Static-class services (`export class XService { static ... }`) and controllers with `try/catch → next(err)`; customer controller/routes use an instance. Folder per domain: `modules/<name>/<name>.{routes,controller,service,validator}.ts`.
- Validate input with Zod (`validateBody`/`validateQuery` or `schema.parse` in controller); throw `AppError` with a stable error code.
- Frontend: React function components, Tailwind classes, `src/services/*Service.ts` over `ApiClient` (`apiClient.ts`, auto-refresh once on 401). Types in `src/types.ts`.
- Tests live in `server/src/tests`, supertest against `app`, `describe/it`, vitest globals on.
- `server/tsconfig.json` excludes tests from `tsc` (tests are type-checked only by Vitest transform, i.e. not at all).
- Match surrounding style; keep comments sparse.

## 22c. P7 (orders/payments) — P7A VERIFIED (2026-10-10); P7B / P7C / P7D NOT IMPLEMENTED
Design review: PROJECT_COMPLETION_ROADMAP.md (Phase 7) and IMPLEMENTATION_STATUS.md. **P7A (policy + order lifecycle foundation) is implemented and verified; P7B (payment provider/verification/webhooks), P7C (cancellation/refunds) and P7D (web payment UI) are NOT implemented** and need explicit approval plus their blocking P7-D decisions.
P7A facts future work must respect:
- `OrderTransitionService` (`modules/order/orderTransition.service.ts`) is the ONLY writer of `Order.status` after creation (a static test fails if any other source calls `order.update*`). It locks the order row, checks the allow-list (`orderStatus.ts`: PENDING, CONFIRMED, ACCEPTED, PREPARING, READY, DISPATCHED, DELIVERED, CANCELLED - no OUT_FOR_DELIVERY), authorizes the actor, enforces payment eligibility, does a compare-and-set update and writes one `OrderEvent` + one `ORDER_STATUS_CHANGED` audit row; same-status requests are no-ops. `PENDING->CONFIRMED` is SYSTEM-only and requires `paymentStatus='PAID'`; ACCEPTED/PREPARING also need `kitchenBranchId`. A PAID order cannot be cancelled until the P7C refund workflow exists. There is no test-only bypass.
- P7B must set `paymentStatus='PAID'` in a trusted verified-payment transaction and then call the transition with `{ kind: 'SYSTEM', source: 'PAYMENT_VERIFICATION' }` passing its `tx`. COD confirmation also belongs to P7B (COD orders stay PENDING in P7A).
- KDS ticket changes and delivery assignment changes call the transition service in the SAME transaction (ticket/assignment change is rolled back if the order cannot move). KOTs only move forward (QUEUED -> PREPARING -> READY -> SERVED); a DELIVERED assignment is final. Nothing creates KOTs or assignments yet (P8/P9) and `Order.kitchenBranchId` is still never set (branch routing, roadmap D8).
- Quantities are validated, never coerced (`INVALID_QUANTITY`, `MAX_LINE_QUANTITY_EXCEEDED`, `MAX_CART_QUANTITY_EXCEEDED`); cart mutations are serialized with checkout by the same customer row lock; a legacy invalid cart row is viewable (`quantityIssues`) but cannot be previewed or ordered.
- `paymentMethod` is validated (`ONLINE` | `COD`; `COD_NOT_ALLOWED` unless policy enables it). The global `express.json` still keeps no raw body: the P7B webhook route must be mounted before it and exempted from the general rate limiter. `AuditService` redaction now also covers signature/cvv/cvc/vpa/card keys.
- `deliveryInstructions` is accepted by the API but is still not persisted on the order (pre-existing).
