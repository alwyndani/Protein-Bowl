Persistent engineering instructions for Claude Code. Everything below was verified against the repository on 2026-10-07 (onboarding audit). ## 1. Purpose
Protein Bowl is a food-tech platform: customer web app, React Native mobile app, one Express REST API, one PostgreSQL database, and internal ERP/operations modules, gated by RBAC. Web and mobile MUST share the same backend and database. This is an existing project migrated from Antigravity IDE — never rebuild, replace architecture, or delete modules that look incomplete.


**PERMANENT PAYMENT POLICY: Protein Bowl supports ONLINE payment only. Cash on Delivery (COD) is not supported and must not be introduced in web, mobile, customer ordering, delivery or future commerce phases (P8/P9/P10/P11 and later).** Backend: `POST /orders` accepts only `ONLINE` (omitted = ONLINE); `COD` is rejected `422 COD_NOT_ALLOWED` (other values `422 INVALID_PAYMENT_METHOD`); `COMMERCE_COD_ENABLED=true` fails startup (the flag only exists so old env files still parse). No delivery cash collection, COD confirmation, COD settlement or COD refund may be built. The string `COD` can still appear on LEGACY order rows (`Order.paymentMethod` is a free String; no enum/migration exists to remove): such rows stay readable, are non-payable online (`payment` = NOT_STARTED/false) and never enable a new COD order. Dormant, non-customer leftovers (mock ERP B2B payment terms such as "Immediate COD" in Bakery/Tepache/Omnichannel dashboards, and the unreferenced `DirectGuestOrderModal`) are not customer ordering paths; do not extend them.

## 4. Backend architecture
- Base path `/api/v1`. Mounted: auth, customers, products, recipes, cart, checkout, orders, mess, diets, kds, procurement, delivery, pos, fmcg, tepache, md, hrm, finance, cms, plus `/admin/*` (SUPER_ADMIN platform administration; MD read-only on branches), `/staff/me|permissions` (staff self-service), `/auth/staff/accept-invite`, plus `GET /health`.
- Layering: `*.routes.ts` (middleware chain) → `*.controller.ts` → `*.service.ts`. Zod validators exist for auth, customer, diet, recipe, cart, order only.
- Response envelope: `{success, message?, data?, error?}`; `ApiResponse` helper in `utils/apiResponse.ts`, though cart/order controllers call `res.json` directly. Errors: throw `AppError(message, status, code)`; `errorHandler` maps `AppError` and `ZodError` (422).
- Monetary logic: `modules/commerce/pricing.service.ts` is the single Decimal-safe pricing authority (cart, checkout preview AND order creation) and takes a **`CommercePolicy`** (`config/commercePolicy.ts`, P7A) - there is NO default policy and no hard-coded fee/threshold/tax rate. Tax is EXCLUSIVE, per line, rounded HALF_UP, order tax = sum of rounded line taxes; delivery/packaging fees and deposits are untaxed.
- Order creation (P7A) is ONE transaction under a per-customer Postgres row lock (`modules/commerce/checkoutLock.ts`, shared with cart mutations): customer-scoped idempotency (`@@unique([customerProfileId, idempotencyKey])`, key REQUIRED via header `x-idempotency-key`, 8-128 chars), `requestFingerprint` (same key + different request -> 409 `IDEMPOTENCY_KEY_REUSED`), pricing with the current policy + immutable `pricingSnapshot`, minimum-order enforcement, OrderItem/address snapshots, `OrderEvent` (null -> PENDING), `ORDER_CREATED` audit, and deletion of exactly the ordered cart lines. Order numbers are `PB-YYMMDD-XXXXXX` (CSPRNG; a collision retries the transaction, 5 attempts then 503 `ORDER_NUMBER_UNAVAILABLE`). Responses are the customer DTO (`order.dto.ts`), never the raw row.
- Prisma: all application services/controllers use the shared singleton (`import { prisma } from '../../config/database.js'`; logs `error`/`warn` only, `error` in production). Never add `new PrismaClient()` to app code. Intentional standalone clients remain only in `prisma/seed*.ts` scripts and test fixtures (`src/tests/*`).

## 6. Authentication
- **The database is the source of truth for every authenticated request (P6A):** `authenticateToken` verifies the JWT signature/expiry, then loads the user; unknown, soft-deleted or non-ACTIVE (PENDING/SUSPENDED/DEACTIVATED) accounts get `401 ACCOUNT_INACTIVE` immediately, and `req.user.roles` is rebuilt from the CURRENT `UserRoleAssignment` rows (JWT role claims are never used for authorization). Refresh (`rotateRefreshToken`) and login also reject inactive/soft-deleted users; refresh denial revokes all of the user's sessions (`AuthService.revokeAllRefreshTokens`) and is audited. Cost: one indexed PK query per request.
- Access JWT (15m default) via `Authorization: Bearer`; refresh token (7d) stored hashed-in-DB (`RefreshToken`), sent as HttpOnly cookie `pb_refresh_token` (the web refresh route still ALSO accepts a body `refreshToken`, but NO web response ever returns one), rotated on refresh (P11A: revoke-old + create-new is ONE transaction). The customer MOBILE app uses the dedicated `/auth/mobile/*` routes (refresh token in the JSON body, see 22l).
- Web keeps access token in memory only (`ApiClient`). Mobile uses expo-secure-store.
- Rate limits (per IP, env-configurable `RL_*`): login 20/15min, register 10/hour, refresh 60/15min, general `/api/v1` 600/15min (health exempt). Limits are effectively off under `NODE_ENV=test` unless a test sets `RL_*_MAX` before importing the app (see `ratelimit*.test.ts`). `RL_DISABLED=true` works only outside production. Set `TRUST_PROXY` when behind a reverse proxy.
- Public registration allows only `CUSTOMER` (P10A: `MESS_CUSTOMER` is refused 422; customer password policy: min 8, unchanged). Staff accounts are created ONLY through the staff lifecycle below (or the CLI bootstrap for the first SUPER_ADMIN) - never by public registration.
- **Staff lifecycle (P6B):** SUPER_ADMIN `POST /admin/staff` (needs step-up) → account `PENDING` with an unusable random placeholder password hash, staff roles + branches, and an invitation → one-time setup link returned ONCE (`deliveryMode: "manual"`, `sentByEmail: false`; nothing is emailed) → staff `POST /auth/staff/accept-invite {token, password}` (public, rate-limited `RL_ACCEPT_INVITE_*`) → in one transaction: invitation consumed, password set, status `ACTIVE`, earlier sessions revoked, `STAFF_INVITATION_ACCEPTED` audited → staff logs in normally. Invitation tokens: 32 random bytes (hex), only the SHA-256 hash is stored (`StaffInvitation.tokenHash`), single use, expire after `INVITE_TTL_HOURS` (default 72h), revocable/reissuable (`POST /admin/staff/:id/invitation`, PENDING accounts only - never a password reset for ACTIVE users). Every invalid/expired/used/revoked/ineligible token returns the same `400 INVALID_INVITATION`. The token travels in the setup link's URL fragment. `INVITE_DELIVERY=manual` is the only supported mode until the email adapter (P14) implements `InvitationDelivery`: it is OPTIONAL (defaults to manual) in development/test but REQUIRED in production - a missing or unsupported value fails config validation at startup (no silent fallback). Manual mode always reports `deliveryMode: "manual"`, `sentByEmail: false` and never claims an email was sent. Any test that simulates a production boot must set `INVITE_DELIVERY=manual` (plus `CORS_ALLOWED_ORIGINS`).
- **Staff password policy (decision D7):** 12-128 chars, ≥3 of 4 character classes unless a 20+ char passphrase, not a known/default password, must not contain the email name or the person's name (`utils/staffPassword.ts`). Staff 2FA is deferred.
- **Password step-up:** `POST /admin/step-up {password}` (SUPER_ADMIN, rate-limited `RL_STEPUP_*`) returns a short-lived proof (`STEP_UP_TTL_SECONDS`, default 300s) sent as `X-Step-Up-Token`. It is a signed JWT with a distinct audience, bound to the user and an HMAC fingerprint of their CURRENT password hash (changing the password invalidates it); `verifyAccessToken` rejects it as an access token. Required for: create staff, reissue invitation, assign/revoke role, assign/revoke BRANCH, deactivate, activate. Not required for staff profile updates or read endpoints. It is time-limited, not single-use (single-use would need server-side storage); step-up tokens never appear in the audit log.

## 7. RBAC roles (`RoleEnum`, verified)
CUSTOMER, MESS_CUSTOMER, SUPER_ADMIN, MD, NUTRITIONIST, TRAINER, CHEF, PROCUREMENT, DELIVERY, POS, BAKERY_FMCG, TEPACHE_ERP, SWIGGY_ZOMATO. Do not change role semantics.
Middleware (`auth.middleware.ts`): `authenticateToken` (DB-authoritative); `requirePermission('kds:read'|…)` (static catalogue in `authz/permissions.ts`; **no implicit SUPER_ADMIN bypass** — SUPER_ADMIN holds permissions explicitly; MD holds READ permissions only); `requireRole([...])` (**staff/admin APIs only — SUPER_ADMIN always passes**); `requireCustomerRole` (literal CUSTOMER; no SUPER_ADMIN bypass); `requireExactRoles([...])` (listed roles only; no bypass). `rbac.middleware.ts` also has `requireRoles` (SUPER_ADMIN bypass; used only in `auth.routes`). RULE: customer-context endpoints must use `requireCustomerRole`/`requireExactRoles`, never `requireRole`.
**Role scope catalogue (`authz/roleScopes.ts`):** SUPER_ADMIN=GLOBAL; MD=GLOBAL_READ (read-only visibility; no operational mutations, staff/role/security administration, or clinical health data); NUTRITIONIST/TRAINER=ASSIGNMENT; CHEF/PROCUREMENT/POS/BAKERY_FMCG/TEPACHE_ERP/SWIGGY_ZOMATO=BRANCH (facility roles get NO global access); DELIVERY=BRANCH_SELF (own work only); CUSTOMER/MESS_CUSTOMER are customer identities. Staff and customer identities stay separate (no account may hold both; `hasMixedIdentity`/`findMixedIdentityUserIds` detect conflicts and only report); CUSTOMER/MESS_CUSTOMER/SUPER_ADMIN are in `NON_ASSIGNABLE_ROLES` for future staff-administration APIs (SUPER_ADMIN is created only by the P6B bootstrap CLI).
**Branch scope (`authz/branchScope.ts`):** `resolveBranchScope` (DB) → `resolveBranchFilter(scope, mode, requestedBranchId)`: branch-scoped callers get their assigned branches; an omitted branch means "my branches" (NEVER all); a foreign branch → 403 `BRANCH_FORBIDDEN`; no assignment → 403 `NO_BRANCH_ASSIGNMENT`; only SUPER_ADMIN (and MD for reads) can get `all`. Applied to the kitchen queue (P8), procurement, POS and delivery endpoints (denials are audited). Delivery (P9A): drivers get the queue of their OWN authorized branches only (a client `driverId` is not accepted at all; a foreign `branchId` → 403 `BRANCH_FORBIDDEN`), private delivery data only for orders they own, and SUPER_ADMIN/MD read ONE explicit branch (see §22f). Use `authorizeBranch` / `assertResourceBranchAccess` in new operational endpoints; never trust a client branchId.
**Administration permissions (P6B, `authz/permissions.ts`):** `staff:admin`, `audit:read`, `branch:write` = SUPER_ADMIN only; `branch:read` = SUPER_ADMIN + MD. MD is NOT a staff/security administrator and cannot read the audit log.
**Role guardrails (`StaffAdminService`):** SUPER_ADMIN/CUSTOMER/MESS_CUSTOMER are never assignable or revocable through the API (`NON_ASSIGNABLE_ROLES`); nobody can change their own roles, branches or deactivate themselves; an account must keep ≥1 role (`LAST_ROLE`); staff targets only (customers are indistinguishable from not found); mixed customer/staff identities are refused (`MIXED_IDENTITY`); duplicate assign / revoking an unheld role are deterministic no-ops (`changed:false`, not audited); role changes take effect on the next request (P6A).
**Branch rules:** assignable branches must exist and be active; `EmployeeBranchAssignment` is authoritative; the first assigned branch becomes the primary (`assignedBranchId`); revoking the primary re-points it to the earliest remaining assignment or clears it (it can never dangle, because scope = assignments ∪ primary). A branch with ACTIVE/PENDING staff cannot be deactivated (`BRANCH_HAS_ACTIVE_STAFF`). Branch `code` is immutable; branches are never deleted.
**Deactivation:** requires a reason; revokes ALL refresh sessions and active invitations; the old access token dies on the next request (P6A); `LAST_SUPER_ADMIN` guard runs in a SERIALIZABLE transaction (concurrent mutual deactivation cannot leave zero administrators). Activation requires a reason, refuses PENDING (use the invitation), soft-deleted, and never-completed-setup accounts (`PASSWORD_SETUP_INCOMPLETE`).
`MESS_CUSTOMER` is LEGACY / DEPRECATED FOR FUTURE RECONCILIATION. Target (decided): CUSTOMER is the canonical customer identity for Customer Portal AND Kerala Mess; Mess entitlement = the customer's MessAccount. P10A: customer Mess endpoints accept ONLY the literal CUSTOMER; legacy MESS_CUSTOMER gets `403 MESS_CUSTOMER_LEGACY_ROLE` (backend-only compatibility pending a controlled conversion, see §22i); MESS_CUSTOMER is not accepted on diet/commerce/profile APIs. Do not delete or rewrite the role without an approved phase.

## 8. Customer vs staff boundaries
One customer account, two customer experiences (Customer Portal, Kerala Mess). Customers never get staff/ERP permissions. Public register cannot mint staff roles. Customer-private routes derive identity from `req.user.userId` (JWT) → `CustomerProfile` lookup; never accept `customerId` from the client. SUPER_ADMIN must not be able to use `/me` customer endpoints (order, checkout, customers/me use `requireCustomerRole`; see §9 for gaps).

## 9. Security rules and known gaps
Rules: backend authorization + ownership checks are authoritative; frontend hiding is not security; never leak costing/clinical notes/SOP/supplier/ERP metadata in public DTOs; least-privilege for health data (diet health-profile access is limited to NUTRITIONIST/SUPER_ADMIN with claim checks in `diet.service`).
Phase 4C (2026-10-07) fixed: cart/diet/mess customer-role guards (SUPER_ADMIN and staff are blocked from customer-context APIs); CORS allow-list + Origin check on state-changing requests (`CORS_ALLOWED_ORIGINS`, falls back to `CLIENT_URL` outside production; production startup fails without it; no-Origin requests such as mobile/curl are allowed; a disallowed origin gets no CORS headers, mutating requests get 403 `ORIGIN_NOT_ALLOWED`); auth + general rate limits; `JSON_BODY_LIMIT` (default 256kb; oversized -> 413, malformed JSON -> 400); invalid HTTP `4404` in mess controller; Payment default; seed production guard (`prisma/seedGuard.ts`: NODE_ENV=production seeds only recipes/products, never demo users); web/mobile demo credentials gated behind `import.meta.env.DEV` / `__DEV__`; shared Prisma singleton.
Body limit rationale: legitimate max today is a 7-day nutritionist plan (~20-45KB); a verbose 30-day, 6-meals/day plan is ~90KB; the validators allow up to 365 days (~1MB) but no UI sends that. Binary/lab-report uploads need a dedicated upload route later, not bigger JSON limits.
P6A (2026-10-08) fixed: S16 (deactivated users / stale roles — see §6), S17 (cross-branch reads/writes), SUPER_ADMIN and MD access to customer health data (see §18), `/auth/rbac-test` is registered ONLY when `NODE_ENV !== 'production'`, and the web role-demo switcher (BrandHeader) is DEV-only; additionally the production web build only presents a staff dashboard to a session that holds the matching backend role (`utils/roleGuard.ts`, presentation hygiene only — the backend authorizes every call). Operational DTOs were minimized (KDS: customer full name only; delivery: order basics + address snapshot).
P6B (2026-10-08) delivered: staff/branch/audit administration APIs, invitation onboarding, step-up, 12-char staff password policy, CLI bootstrap, `/staff/me`, audit-read API (SUPER_ADMIN-only, payload re-sanitized on output). Audit events: STAFF_CREATED, STAFF_INVITED, STAFF_INVITATION_REISSUED, STAFF_INVITATION_ACCEPTED, STAFF_INVITATION_REJECTED, STAFF_UPDATED, STAFF_ACTIVATED, STAFF_DEACTIVATED, ROLE_ASSIGNED, ROLE_REVOKED, BRANCH_ASSIGNED, BRANCH_REVOKED, BRANCH_CREATED, BRANCH_UPDATED, BRANCH_DEACTIVATED, SUPER_ADMIN_BOOTSTRAPPED, STEP_UP_FAILED, STEP_UP_DENIED, ADMIN_ACTION_DENIED (+ P6A events). Notes: trimmed, control/zero-width characters stripped, max 200. Bodies are STRICT zod schemas: an amount/currency/payment/customer id is rejected, never ignored.
- **FULL refunds only** (the complete captured amount; no fee/deduction, no tax recalculation, Razorpay `normal` speed). Amount, target payment and currency are server-derived under the Order -> ProviderPayment locks; the partial unique index allows ONE live non-EXTERNAL refund per ProviderPayment (PROCESSED still occupies it; only an explicitly ABANDONED intent frees the slot).
- **PB refund states:** REQUESTED -> SUBMITTING -> PROCESSING -> PROCESSED, plus UNKNOWN, REVIEW, ABANDONED. There is NO PB FAILED state: provider failure stays in providerStatus/failureCode/failureReason and the refund goes to REVIEW. PROCESSED is monotonic. Table in `refundStatus.ts`.
- **Atomic cancellation:** ONE transaction: lock Order -> lock the applied ProviderPayment -> validate -> create the Refund REQUESTED -> `OrderTransitionService` -> audit -> commit. The transition accepts a paid cancellation ONLY with a real REQUESTED refund id of the same order (`refundIntentId`, passed only by `CancellationService`; static test) from CONFIRMED/ACCEPTED. The provider is contacted only AFTER the commit (best effort via `PAYMENT_REFUND_INLINE_SUBMIT`); the reconciliation worker guarantees submission. Unpaid cancellation: no refund; PENDING checkout sessions become EXPIRED (kept for history/late-capture reconciliation).
- **PAYMENT_REFUND_INLINE_SUBMIT (latency only):** true = after a cancellation COMMITS, also try to submit the refund in the background (`RefundService.kick`); false = leave it to the reconciliation worker. Inline and worker call the SAME `RefundService.submit` (row lock + REQUESTED -> SUBMITTING compare-and-set + lease), so the setting can never change financial correctness and the cancel API never waits for the provider. Validated exactly `true`|`false`; REQUIRED explicitly in production (no hidden default), development/test default true.
- **SUBMITTING crash window:** if the provider created the refund but the answer was lost and the process died, the refund stays SUBMITTING under a lease. Other workers ignore it until the lease expires; then the worker moves it SUBMITTING -> UNKNOWN (`SUBMIT_LEASE_EXPIRED`) and LOOKS UP by exact receipt (+ payment, amount, currency) -> PROCESSING. It is never re-created: createRefund is called exactly once (tests 45, 86, 87).
- **Outside (EXTERNAL) refunds vs a local refund:** a local REQUESTED refund is refused BEFORE any provider call (-> REVIEW `EXTERNAL_REFUND_PRESENT`) when an outside refund exists for the payment; an intent is refused when one exists at creation. The only unpreventable window (both already at the provider) is flagged `OVER_REFUNDED` with an alert.
- **ABANDON safety:** only from REVIEW, with operator + reason + `--confirm-absent-at-provider`, AND the intent's own history must PROVE nothing exists: either the provider was never called (external-refund guard) or it gave a documented "nothing created" rejection (`providerStatus=REJECTED`; duplicate/"already" texts and unknown texts never qualify). Then the provider is listed again: outage, an exact receipt match, any ambiguity, a known provider refund id, or EXTERNAL refunds all refuse. A refund that reached REVIEW from a timeout/lost answer/ambiguity can NEVER be abandoned: an empty listing is not proof.
- **Idempotency:** Refund.id is the provider receipt. The single provider create call is guarded by the REQUESTED -> SUBMITTING compare-and-set and is NEVER repeated. Timeout/5xx/unreadable/crash/DB failure after provider success = UNKNOWN; recovery lists the payment's provider refunds and matches the EXACT receipt (+ payment, amount, currency); an EMPTY listing is not proof of absence; ambiguity/unresolved past the review window = REVIEW. A duplicate-receipt rejection triggers lookup, never a second create.
- **Settlement:** every refund evidence source (API answer, webhook, reconciliation, manual) goes through `RefundSettlementService.apply`. When the FULL refund of the order's EFFECTIVE payment is PROCESSED it sets `Order.paymentStatus=REFUNDED` (never `Order.status`; static test) and the ledger row REFUNDED. Duplicate / after-cancellation refunds never change the order's payment state.
- **Duplicate capture / payment after cancellation:** never refunded automatically. `POST /admin/provider-payments/:id/refund` (SUPER_ADMIN + step-up) creates the full refund for that exact DUPLICATE or AFTER_CANCELLATION ledger row; the applied payment can never be the target. AUTHORIZED-only payments are never refunded (no capture/void feature); a later capture follows AFTER_CANCELLATION.
- **EXTERNAL refunds** (made outside Protein Bowl, proven by trusted provider evidence on a known payment) are ledgered as `trigger=EXTERNAL`, counted as refunded money, flagged `EXTERNAL_REFUND` for review (CLI `refund-ack-external` after review) and block a PB full refund (`EXTERNAL_REFUND_PRESENT`).

## 22g. P9B facts (Delivery Code: verified delivery completion; VERIFIED and COMMITTED (430124e); backend 852, web 455 tests; **14 migrations** (one new: `20261011180025_p9b_delivery_proof`, purely additive))
- **What it is:** a server-generated, cryptographically random **6-digit Delivery Code** (NOT an SMS OTP: there is no SMS/email/push channel). The code proves PHYSICAL HANDOVER only, never payment. The ONLY ways an order becomes DELIVERED: the assigned DELIVERY employee enters the customer's valid code, or the exceptional SUPER_ADMIN override. P9B completes DISPATCHED -> DELIVERED; retry / redelivery / post-dispatch reassignment / returns / refunds are **P9C — Failed Delivery Resolution (NOT started, needs approved policy)**.
- **Generation:** `crypto.randomInt(0, 1_000_000)` left-padded; never derived from order/customer/driver/time/secret. Created lazily ONLY when the owning CUSTOMER asks while the order is DIRECT + ONLINE + PAID + DISPATCHED (never at payment, READY, claim or dispatch).
- **Storage (`DeliveryProof`, one row per ORDER, unique `orderId`, RESTRICT foreign keys, no backfill):** `codeHash` (nullable: only an override on an order whose code was never issued), `codeVersion`, `issuedAt` (current code), cumulative `regenerationCount` (CHECK 0..10), `regenerationWindowStartedAt` + `regenerationsInWindow` (hourly window, CHECK 0..3), per-CURRENT-code `failedAttempts` (0..5) / `lockCycles` (0..3) / `lockedUntil` / `blockedAt`, completion evidence `verifiedAt` + `method` (PIN | ADMIN_OVERRIDE) + `verifiedByEmployeeId` / `overrideByUserId` / `overrideReasonCode` / `overrideNote` / `previousAssignmentStatus`. CHECK constraints are hand-appended in the migration (Prisma cannot express them; `migrate diff` ignores them): replayed by `p9b.migration.test.ts`. Existing DISPATCHED orders simply have no row (customer state NOT_ISSUED); nothing is auto-delivered.
- **Hashing:** `HMAC-SHA256(DELIVERY_PROOF_SECRET, "pb-delivery-code|v1|<orderId>|<codeVersion>|<code>")`, constant-time compare. `DELIVERY_PROOF_SECRET` (`config/deliveryProofConfig.ts`): REQUIRED in production (>= 32 chars, startup fails closed), labelled dev fallback otherwise, never committed/logged/returned. A leaked DB alone cannot brute-force the 10^6 space without the secret; rotating it invalidates outstanding codes (customers re-issue).
- **Plaintext lifetime:** returned ONLY by issue / regenerate (`Cache-Control: no-store`) and held in the customer component's memory. After a reload the customer sees ISSUED but never the old digits (they generate a new code). Never in DB, logs, AuditLog, errors (the code field is a plain bounded string: Zod never echoes it), analytics or browser storage.
- **Customer API (literal CUSTOMER owner, 404 for others, `modules/delivery/deliveryCode.routes.ts` mounted under `/api/v1/orders`):** `GET /:orderId/delivery-code` (state `NOT_AVAILABLE | NOT_ISSUED | ISSUED | LOCKED | CODE_BLOCKED | VERIFIED` + `issuedAt`/`lockedUntil` only), `POST /:orderId/delivery-code` (ISSUE only; a repeat/double click is 409 `DELIVERY_CODE_ALREADY_ISSUED`, it never silently changes the code), `POST /:orderId/delivery-code/regenerate` (needs an issued code; bumps `codeVersion` so the old code dies at once; resets the CURRENT code's attempts / cycles / lock / block; `regenerationCount` is never reset, lifetime cap 10 -> `DELIVERY_CODE_REGENERATION_LIMIT`).
- **Regeneration throttle (persisted, database-authoritative):** at most **3 regenerations per hour per order** and **10 per order lifetime**, both enforced in `DeliveryProofService.regenerate` under the Order -> DeliveryProof row locks, so every backend instance reaches the same result. Fields on `DeliveryProof`: `regenerationWindowStartedAt` + `regenerationsInWindow` (the hourly window; CHECK 0..3, <= `regenerationCount`, counter 0 <=> no window) and the separate cumulative `regenerationCount` (CHECK 0..10, never reset). FIXED window: the first regeneration sets the start = now and the counter = 1; while `now < start + 1 h` each success increments it and a request with the counter already 3 is refused `429 DELIVERY_CODE_REGENERATE_LIMIT`; once the hour has elapsed the next success starts a fresh window (start = now, counter = 1). A refused request writes NOTHING (codeVersion, hash, issuedAt, counters, attempts/lock all unchanged). The lifetime cap (409 `DELIVERY_CODE_REGENERATION_LIMIT`) is independent. The earlier 60-second minimum interval was REMOVED (it would have been a third overlapping policy). The per-user+order middleware limiter `RL_DELIVERY_CODE_REGEN_*` (3/h) remains only as a secondary per-process defence; correctness never depends on it. AuditLog is evidence only, never a counter. Issue and regenerate are separate endpoints, so a double click on ISSUE never regenerates.
- **Driver API:** `POST /api/v1/delivery/orders/:id/verify-delivery` body `{ code }` (strict; "123456", "123 456", "123-456" normalized server-side; anything not 6 digits is a fixed 422 `INVALID_DELIVERY_CODE_FORMAT` that is NOT counted). Exact DELIVERY role + `delivery:write` + own assignment + authorized branch + DIRECT + ONLINE + PAID + Order DISPATCHED + assignment **IN_TRANSIT** (a FAILED assignment is refused `409 DELIVERY_IN_EXCEPTION`: FAILED is an operational exception, never silently revived) + code issued + not locked + not blocked. Non-owner / foreign branch / unknown = the same 404 as P9A. SUPER_ADMIN, MD, CHEF, CUSTOMER cannot use it (403). Success response is minimal `{changed, order:{id, orderNumber, status:'DELIVERED', deliveredAt}}` (no PII added); the order then leaves the driver queue.
- **Attempt policy (database authoritative, `deliveryProof.service.ts`):** 5 wrong codes -> 15-minute lock (same duration every cycle; counters committed, the safe error is thrown AFTER commit); after the lock a new 5-attempt window; after the 3rd lock cycle the current code is permanently BLOCKED until the customer regenerates. Parallel guesses serialize on the order lock then the proof-row lock (10 parallel wrong guesses = exactly 5 counted). A verification that ARRIVED before a concurrent regeneration committed is answered `409 DELIVERY_CODE_CHANGED` and is NOT charged to the new code (`receivedAt` is taken in the controller before any lock wait; `issuedAt > receivedAt`). Replay by the owner with the correct code after delivery = `changed:false`; a wrong code after delivery = 409 `ALREADY_DELIVERED`, not counted. Equivalent security history: `regenerationCount` (cumulative) + the audit trail; per-code counters reset on regeneration (max exposure ~11 codes x 15 attempts).
- **Guarded DELIVERED transition:** `TRANSITION_PARTIES['DISPATCHED->DELIVERED'] = ['DELIVERY_PROOF']` (an internal party; NO human role is listed). `OrderTransitionService` accepts only a `PROOF` actor, requires the caller's transaction, and independently verifies a `DeliveryProof` row of THE SAME ORDER with `verifiedAt` set and the same `method`, ONLINE, and PAID (re-read under the lock). Constructing `{kind:'PROOF'}` proves nothing. Static test: only `deliveryProof.service.ts` constructs a PROOF actor / names `'DELIVERED'` (besides the status catalogue and the transition itself); nothing writes `Order.status` directly.
- **Atomic completion (lock order Order -> DeliveryProof; the assignment is covered by the order lock):** proof evidence + assignment `DELIVERED` + `deliveryTime` + `OrderTransitionService` (OrderEvent + `ORDER_STATUS_CHANGED`) + `DELIVERY_VERIFIED` audit in ONE transaction; exactly one effective completion (parallel verifies, verify vs override, override vs failure, verify vs failure are all serialized and tested).
- **SUPER_ADMIN exceptional override:** `POST /api/v1/admin/orders/:orderId/delivery-override` (permission `delivery:override`, SUPER_ADMIN only, step-up `delivery.override`, rate limit 5/15 min per user). Strict body `{reasonCode (CUSTOMER_CANNOT_ACCESS_CODE | CUSTOMER_DEVICE_UNAVAILABLE | CODE_VERIFICATION_FAILURE | ACCESSIBILITY_ASSISTANCE | OPERATIONAL_EXCEPTION | OTHER), note (sanitized, 10-200), confirm: true}`. Order must be DIRECT + ONLINE + PAID + DISPATCHED and the assignment IN_TRANSIT or FAILED. It goes through the SAME proof-backed transition (`method=ADMIN_OVERRIDE`); from FAILED it records `previousAssignmentStatus='FAILED'` and keeps the failure `deliveryNotes` and failure audit. Audit `DELIVERY_OVERRIDE_APPLIED` (reason code, previous state, method; never the note text). It is NOT routine delivery completion and SUPER_ADMIN has no normal-edge authority.
- **DTOs:** driver (`proof: {state: CODE_NOT_ISSUED | READY_FOR_VERIFICATION | LOCKED | CODE_BLOCKED | VERIFIED, lockedUntil}`; no attempt counts), monitor (`proofState`: NOT_ISSUED | ISSUED | LOCKED | CODE_BLOCKED | VERIFIED | OVERRIDDEN), customer (above). None carries the code, hash, version, counters, lock cycles, regeneration count or override internals (tested on every payload).
- **Audit events:** `DELIVERY_CODE_ISSUED`, `DELIVERY_CODE_REGENERATED`, `DELIVERY_VERIFY_FAILED`, `DELIVERY_VERIFY_LOCKED`, `DELIVERY_CODE_BLOCKED`, `DELIVERY_VERIFIED`, `DELIVERY_OVERRIDE_APPLIED` (+ `ORDER_STATUS_CHANGED`). ## 22k. P10C facts (Kerala Mess bulk delivery, service-point handover, fulfilment and completion; VERIFIED in the working tree, NOT YET COMMITTED; backend 1141, web 548 tests; **18 migrations** (one new: `20261013120000_p10c_mess_delivery`))
- **Scope:** CHEF releases a READY batch -> ONE DELIVERY employee delivers it to the service points -> a secure per-stop handover -> the meals become FULFILLED -> the subscription COMPLETES. P11 (mobile) is NOT started; `apps/mobile` untouched. NO financial effect anywhere (no payment, COD, cash, pay-at-hostel/gate, driver collection, refund, wallet or compensation; a delivery failure is an operational fact only).

- **Release (CHEF only):** `POST /api/v1/mess/kitchen/batches/:id/release` (exact CHEF, `mess:kitchen:write`, authorized branch, batch READY, mealDate >= today). Customer routes: `GET|POST /mess/subscriptions/:id/meals/:mealId/handover-code` and `POST .../regenerate` (no run / stop id is ever exposed to the customer).
- **Verify (owner DELIVERY, run IN_TRANSIT, stop PENDING, same business date):** lock order run -> stop -> meals (id order); on success the stop becomes HANDED_OVER (method CODE) and EXACTLY the stop's frozen SCHEDULED meals become FULFILLED with `fulfilledAt`; the count must equal the frozen `expectedQuantity` or EVERYTHING rolls back (`STOP_QUANTITY_MISMATCH`). All-or-nothing: no partial quantity. Replay by the same driver = `changed:false`; two simultaneous verifications = one handover.
- **Failure / retry:** fixed reasons SERVICE_POINT_CLOSED | RECIPIENT_UNAVAILABLE | CODE_NOT_AVAILABLE | UNABLE_TO_REACH | VEHICLE_ISSUE | QUANTITY_MISMATCH | OTHER (note required for OTHER, never shown to customer / MD). A failure fulfils nothing, kills the proof and touches no money. Retry (owner): FAILED -> PENDING, `attemptCount` + 1, `codeVersion` + 1, recipient and proof cleared; **attemptCount is the number of the CURRENT attempt (starts at 1) and a retry is refused once it is already 3** (so at most 3 attempts; DB CHECK 1..3).
